# Разведка API

Эндпоинт: `GET http://final-project.simulative.ru/data?date=YYYY-MM-DD`. Отдаёт JSON-массив строк покупок за один день без пагинации.

## Схема записи

```json
{
  "client_id": 996727,
  "gender": "M",
  "purchase_datetime": "2023-01-15",
  "purchase_time_as_seconds_from_midnight": 22967,
  "product_id": 7781,
  "quantity": 26,
  "price_per_item": 95965,
  "discount_per_item": 39404,
  "total_price": 1470586.0
}
```

9 полей, без вложенных объектов. `total_price = (price_per_item - discount_per_item) * quantity` — проверено на выборке, расхождений нет. Данных о товаре кроме `product_id` нет: ни названия, ни категории. Данных о клиенте кроме `gender` тоже нет.

## Объём

Дневной объём сильно скачет: на разных днях от ~1600 до ~9700 записей. Валидный диапазон дат — **с 2022-01-01**  до текущей даты и дальше (см. ниже). Бэкфилл 2022-01-01 → вчера — это больше 1000 дней, то есть по грубой прикидке несколько миллионов строк.

## Валидация даты 

- Дата раньше 2022-01-01 → HTTP 200, тело — текст на русском: «Информация за более ранние периоды отсутствует».
- Дата из будущего (пробовал 2030-01-01) → HTTP 200, отдаёт полноценные сгенерированные данные.
- Произвольная строка вместо даты (`date=notadate`) → HTTP 200, данные тоже генерируются, `purchase_datetime` в ответе равен переданной строке как есть.
- Параметр `date` не передан → HTTP 200, текст: «Для выполнения запроса требуется передать в теле параметр 'date' в формате 'YYYY-MM-DD'».

Сервер не отклоняет некорректный ввод — валидность даты (`>= 2022-01-01` и `<= вчера`) должны проверять сами extract/backfill скрипты.

Отдельно: `Content-Type` в ответе всегда `text/html`, даже когда тело — валидный JSON. Различать успех/ошибку нужно по содержимому (JSON-массив vs текстовая строка), не по заголовку.

## Повторные запросы на одну дату

Одна и та же дата, два запроса подряд: набор записей (как множество) идентичен, но **порядок записей в массиве разный** между вызовами. Загрузка в БД — по датам, через upsert/`ON CONFLICT`, а не простой insert: повторный прогон таска или бэкфилла на ту же дату не должен плодить дубли.

## Скорость и параллелизм

Время ответа на один день — от 0.2с (для дат с текстовой ошибкой) до ~30с для валидных дней, разброс большой и не всегда объясняется размером ответа. Таймаут на запрос — не меньше 60с, с retry. 5 параллельных запросов прошли без rate-limit, но каждый запрос при этом стал заметно медленнее (~31-34с вместо одиночных 3-10с) — общее узкое место на сервере. Бэкфилл на 1000+ дней с такой скоростью — это часы, не минуты, скрипт должен уметь резюмироваться после обрыва.
