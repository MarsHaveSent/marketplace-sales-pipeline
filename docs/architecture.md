# Архитектура проекта

## Постановка задачи

Данные о продажах маркетплейса доступны через API, отдающее по одному дню за запрос. Задача: собрать пайплайн, который ежедневно забирает вчерашние данные, хранит историю в БД и кормит BI-дашборды, плюс провести два аналитических исследования на данных за 2023 год.

## Поток данных

```
API (по одному дню) → extract.py → raw.* (JSONB как есть) → dbt staging → dbt marts → Metabase / DataLens / analysis-ноутбуки
```

Raw-слой хранит ответ API «as is», без предположений о финальной схеме — на момент разведки API финальный формат ещё не был известен. Схема фиксируется на уровне dbt-моделей, а не таблицы приёма данных.

## Оркестрация

- **Airflow DAG** (`dags/sales_pipeline_dag.py`): `extract → load_raw → dbt run → dbt test → log_pipeline_run`, ежедневно в 07:00. Про падения — письмо на почту (изначально планировался Telegram, но с этого хостинга API Telegram недоступен — заблокирован на уровне сети).
- **dbt запускается через `BashOperator`** внутри Airflow-контейнера (`dbt run`/`dbt test` как shell-команда).
- **Backfill** (`scripts/backfill.py`) — отдельный одноразовый скрипт для заполнения истории, запускается вручную, переиспользует общий код extract/load.
- **`pipeline_runs`** — таблица с метриками каждого прогона (сколько строк, время выполнения, статус) — основа health-дашборда в DataLens.

## Инфраструктура

- Всё поднимается через **Docker Compose** одной командой: Postgres, Airflow, Metabase.
- **Airflow и dbt ставятся в свои Docker-образы через собственные `requirements-*.txt`**, а не через общий Poetry-проект: у Airflow свои ограничения под конкретную версию, плохо совместимые с обычным резолвером зависимостей. Poetry (`pyproject.toml`/`poetry.lock` в корне) управляет зависимостями только для прикладного кода: `scripts/`, `tests/`, `analysis/`.

## BI

- **Metabase** — основной бизнес-дашборд (продажи, ассортимент, клиенты).
- **Yandex DataLens** — health-дашборд пайплайна на основе `pipeline_runs`, отдельно от бизнес-дашборда в Metabase.

## CI/CD

- **CI** (`.github/workflows/ci-cd.yml`, job `test`): ruff + black + pytest на каждый пуш. Для тестов, требующих БД (например, `load.py`), в CI поднимается Postgres как service-контейнер.
- **CD** (job `deploy`, зависит от `test`, срабатывает только на `main`): по SSH на сервере выполняется `git pull --ff-only && docker compose up -d --build`. Никогда `down`/`down -v` — чтобы не терять volume с данными Postgres при обновлении. Секреты SSH — в GitHub Secrets; `.env` с реальными паролями существует только на сервере и в репозиторий не попадает.

## Безопасность сервера

Firewall (UFW) открыт только на необходимые порты: 22 (SSH), 5432 (Postgres — нужен внешним BI-инструментам и для сдачи доступов), 3000 (Metabase). Airflow UI (8080) наружу не выставляется — используется только через SSH-туннель.

## Тестирование

`pytest` + `requests-mock`/`responses` для мока ответов API + `freezegun` для детерминированных тестов даты. `pre-commit` (ruff/black) — проверка стиля до коммита.

## Аналитическая часть

Оба исследования оформлены как Jupyter-ноутбуки (код + графики + текстовые выводы в одном файле, рендерятся на GitHub), с экспортом в HTML/PDF в `analysis/exports/` как самодостаточный документ для сдачи:

- `01_assortment_abc_xyz.ipynb` — ABC/XYZ-анализ ассортимента + эластичность спроса к скидкам
- `02_customers_ltv.ipynb` — RFM-сегментация + когортный анализ retention

Отдельно — `00_pygwalker_eda.ipynb`: разовый визуальный анализ через [pygwalker](https://github.com/Kanaries/PyGWalker) перед тем, как фиксировать гипотезы для основных исследований.
